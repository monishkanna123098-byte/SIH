## D. Defects — recorded, NOT fixed

### D1 — the live extraction has still never been watched
**Severity: high for the claim, zero for the demo.** This is the same gap
reported at the end of chunk 8 and it is still open.

**What is wrong.** Automated extraction is presented as a working feature and
is covered by 69 checks, every one of which runs against an injected fake
backend. No request has ever left this machine for either provider. Two of the
four failure branches — **a bad key, and a malformed response from a live
provider** — have never been observed; the other two (no key, unreachable
network) have, because they need no credentials.

**Reproduce.**
```bash
python3 -c "import sys; sys.path.insert(0,'.'); from app import vision; print(vision.configured())"
# -> None
ls .env            # -> no such file
```

**Consequence if it is wrong.** If the live path is broken — a rejected
parameter, an unexpected response shape, a model that ignores the JSON
instruction — it fails in front of the judges, on the one feature that involves
a network. The failure is contained (every branch falls back to manual entry,
verified) but it would be visible.

**Proposed action, not taken.** Before the round, someone with a key sets
`LM_VISION_PROVIDER`, `LM_VISION_API_KEY` and `LM_VISION_MODEL`, photographs a
real packet, and runs one extraction through `/upload`. Then repeats with a
deliberately wrong key. Two minutes, no code change. **If nobody does this,
demo the manual path and do not press the button** — the manual path is a
first-class input and is fully verified offline.

### D2 — the OCR cross-check depends on a system package nothing declares
**Severity: low.** Cosmetic on the day; a silent capability loss otherwise.

**What is wrong.** `vision.ocr_text()` needs the `tesseract` binary, not just
`pytesseract`. `requirements.txt` lists `pytesseract` under OPTIONAL but cannot
express the binary dependency. On a machine without it the cross-check returns
`""`, `crosscheck_verbatim` is skipped, every field stays
`verbatim_confirmed=None`, and nothing anywhere says the feature is inactive.

**Reproduce.** On a machine without `tesseract-ocr`: run an extraction; the
response carries `"ocr_available": false` and no field is ever marked
`reported by the model but not found by OCR`. Nothing in the UI distinguishes
this from "every value was confirmed".

**Consequence if it is wrong.** The differentiator that no competing entry has
is invisible, and looks like it was never built.

**Proposed action, not taken.** `apt-get install tesseract-ocr` on the demo
machine, and confirm with the check in item 10 above. Surfacing "cross-check
not available on this machine" in the UI is a code change and is **not**
proposed for tonight.
